Do Mock

à Integração Real

Fechando o ciclo do MVP — e deixando isso visível no Git

PEI V · Prof.: Diego Ramos Inácio

Um padrão que apareceu em mais de um repositório 🚨

const [agendamentos, setAgendamentos] = useState(mockAgendamentos); // Na integração, troque o valor inicial pela API
Essa troca nunca aconteceu. O comentário virou documentação de uma dívida que ninguém pagou.
  • A tela funciona perfeitamente na demo
  • O backend existe no repositório — mas o próprio README dele diz "ainda não há endpoints de negócio configurados"
  • O Pull Request que "entrega" a tela só mexe em arquivos de frontend, sem descrição do que foi feito

Por que isso acontece 💭

Vem direto do que vimos na aula passada: a IA gera a tela bonita e funcional com dado fixo em segundos. Ligar isso ao backend de verdade dá mais trabalho — schema, rota, tratamento de erro — e sempre fica "pra depois".

O "depois" não chega porque a demo já parece pronta.

Regra prática: "mock é uma etapa do processo, não o produto final."

Mock vs. Integração real — como diferenciar 🔍

mock
import mockData from './dadosficticios.js'; const [dados] = useState(mockData);
Nenhuma chamada de rede. O dado nunca sai do arquivo local.
integração real
const res = await fetch('/api/pacientes/1/agendamentos'); if (!res.ok) throw new Error('API indisponível'); const dados = await res.json();
Chama o backend de verdade e trata o caso de erro — não só o caminho feliz.

Commits como evidência de equipe 👥

git log --oneline feature/dashboard 4 commits, 1 autor, grupo de 5 pessoas
Padrão encontrado em mais de uma entrega: a branch existe, o PR existe — mas só uma pessoa aparece como autora de tudo.
Critério oficial do PEI V (README do repositório da disciplina)
"A pontuação é individual: a entrega pertence ao grupo, mas a nota de cada aluno considera sua participação comprovada no projeto (commits, Pull Requests, revisões e demais evidências rastreáveis no repositório), não apenas o resultado entregue pelo grupo como um todo."

PR sem descrição = nota sem evidência 📝

PR ruim
Título: "Feature/dashboard paciente" Descrição: _No description provided._
Ninguém de fora do grupo consegue saber o que foi feito, por quem, nem por quê.
PR bom
O que foi feito: Por que (qual parte do MVP resolve): Como testar: Quem fez o quê:
Esse template, preenchido de verdade, é a evidência de participação que conta na nota.

Atividade prática 🧪

1 Em grupo, abram o próprio repositório e rodem o checklist técnico (slide 6) no PR mais recente.
2 Verifiquem o histórico de commits da branch: quantos autores diferentes aparecem de verdade?
3 Abram uma Issue registrando o que falta para a integração ficar real (e quem vai fazer o quê).

Conclusão

Mock é uma ferramenta válida para testar a tela rápido — mas o MVP só está pronto quando ele conversa de verdade com o backend e isso aparece no histórico do Git como trabalho de todo o grupo.

  • Mock é etapa, não entrega final
  • Integração real = frontend + backend + banco, todos no código
  • PR com descrição e commits de todos = evidência que conta na nota
  • Diagrama de arquitetura é parte do entregável, não pedido avulso
